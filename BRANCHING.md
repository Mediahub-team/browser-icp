# Версионирование, коммиты и ветки

Как мы храним историю исследования так, чтобы **в любой момент откатиться в нужную
точку** и **сравнить расходящиеся линии** пайплайна.

Принцип. Пайплайн линейный (этапы 0→9), каждый этап строится на предыдущем. Значит:
- любой коммит = воспроизводимая точка, к которой можно вернуться;
- развилка на раннем этапе меняет всё ниже по течению → такие развилки живут в
  отдельных ветках, чтобы можно было увидеть, насколько по-разному всё сходится в итоге.

---

## 1. Правило коммитов (commit-per-run)

**После каждого прогона или значимого результата — коммит.** Один коммит = один
логически целостный шаг: один прогон, один сгенерированный артефакт, одно осмысленное
изменение. Не копим изменения «пачкой» и не смешиваем два этапа в одном коммите.

Формат сообщения:

```
[s<N>] <краткая суть>

What:  что сделали — артефакты, файлы
How:   как — метод, входные данные, какой гайд/допущение
Why:   зачем / на основе чего — фидбек, вывод предыдущего этапа
Stage: этап N — <папка> [· развилка: <slug>]
Back:  что эта точка позволяет зафиксировать / к чему откатиться
```

- `[s<N>]` — номер этапа (`s0`…`s9`). Для сквозных/инфраструктурных изменений — `[meta]`.
- Заголовок ≤ 72 символов, назывной или повелительный.
- Каждый коммит самодостаточен: по сообщению понятно **что, как и в какой части
  пайплайна** сделано, без чтения диффа.

## 2. Модель веток

**Четыре ортогональные оси изменений — не путать** (концептуально — [`PLAN.md`](PLAN.md) §3):

| Ось | Что меняется | Имя | Направление |
|---|---|---|---|
| **Позиционирование** | угол продвижения над **той же** функциональностью | `cycle/<vision>` | параллельно (форк) |
| **Реализация / функциональность** | эволюция 0.1 (впитывание фич из офферов) | `version/<version-name>` | вперёд (итерация) |
| **Развилка этапа** | допущение внутри этапа (мотив, гайд, офферная стратегия) | `s<N>/<slug>` | параллельно (форк) |
| **Прогон** | отдельное исполнение/переисполнение этапа | суффикс `-v<x>` (+ лёгкая ветка `run/s<N>-<descr>`) | повтор |

### Ствол
- **`main`** — канон. Только согласованная, «победившая» линия. Базовый best-path для демо и следующих итераций.

### Форк позиционирования — `cycle/<vision>`
- Другой **угол** ([`PLAN.md`](PLAN.md) §2.0 «функциональность ⟂ позиционирование») поверх **неизменной** 0.1.
- Форкается от `main`; переиспользует функциональность без изменений; расходится с 0.2 и ниже.
- Примеры: `cycle/new-vision` · `cycle/new-vision-v2` · `cycle/new-vision-v3`.

### Итерация реализации — `version/<version-name>`
- **Эволюция функциональности вперёд во времени**: новая версия `product-functionality.md`, впитавшая
  возможности из офферов прошлой итерации (петля 7→0, см. §4). Это **не** новый угол — угол может остаться тем же.
- Отличать от `cycle/`: форк проверяет **разные углы над одной сборкой**; `version/` — **одна линия, развивающаяся сборка**.

### Развилка этапа — `s<N>/<fork-slug>`
- Развилка на этапе N с конкретным допущением; форкается от точки, где всё выше зафиксировано;
  несёт верхние артефакты **без изменений**, расходится со своего этапа и ниже.
- Примеры: `s1/motive-cashback` · `s4/guide-custdev-first` · `s7/offer-trust-first`.

### Прогоны — суффикс `-v<x>`
- Отдельное исполнение/переисполнение этапа маркируется суффиксом **`-v<x>`** в именах артефактов/папок
  (напр. `run-custdev-v2-<date>/`, `comparison-v2-<date>.md`). `-v2` = второй прогон.
- Для одноразового эксперимента без долгоживущей линии — лёгкая ветка `run/s<N>-<descr>`, сливаем или выкидываем.

## 3. Рабочий цикл

```bash
# 1. зафиксировали этапы 0–3 в main, делаем развилку на этапе 4
git checkout main
git checkout -b s4/guide-custdev-first

# 2. прогон + коммиты по правилу из §1
git add 05-simulations/ && git commit -m "[s5] прогон custdev v2 на 40 респондентах
...
Stage: этап 5 — 05-simulations/ · развилка: guide-custdev-first
Back:  базовый прогон до анализа"

# 3. вторая линия развилки — от той же точки
git checkout main && git checkout -b s4/guide-problem-first
```

### Сравнить развилки

Диффим downstream-артефакты двух веток от общей точки:

```bash
git diff s1/motive-assistant..s1/motive-cashback -- 06-analysis/ 09-results/
git diff --stat main..s7/offer-aggressive-cb -- 07-offers/ 08-ads/ 09-results/
```

Итог сравнения фиксируем заметкой в `09-results/` (что разошлось, какая линия сильнее
по сигналам/метрикам и почему).

### Откатиться

```bash
git log --oneline                 # найти точку по сообщению [sN]
git checkout <sha> -- <path>      # вернуть конкретный артефакт
git switch -c rollback/<descr> <sha>   # или поднять всю точку как ветку
```

### Что мёрджим обратно

Победившую развилку вливаем в `main` (merge или cherry-pick артефактов). Проигравшие
**оставляем как ветки-архив** — это история принятых решений, не удаляем. В
`PIPELINE.md` отмечаем, какая развилка стала каноном и почему.

## 4. Эволюция функциональности (петля офферы → 0.1)

Функциональность — корень пайплайна, но **между итерациями** она растёт: зашедший оффер (этап 7) —
выражение валидированного спроса, он **предлагает новую возможность**.

**Процесс приёмки:**
1. Оффер фиксирует кандидата в поле **«Подразумеваемая возможность»** ([`templates/offer-template.md`](templates/offer-template.md)).
2. На **новой итерации** заводим ветку `version/<version-name>` от канона.
3. Кандидат вносится в **палитру** `product-functionality.md` (через задел §7 → §3) со **ссылкой на
   оффер-источник** (`← offer-<slug>`). Текущую версию файла не правим — изменение живёт в новой версии.
4. Коммит: `[s0] функциональность <version-name>: + <возможность> (← offer-<slug>)`; провенанс — в теле (`Why:`).
5. Downstream перегоняется на новой версии (прогоны — с суффиксом `-v<x>`).

**Дисциплина трассировки:** петля **межитерационная** — DAG внутри итерации остаётся ацикличным
([`VAULT.md`](VAULT.md) §5). Не строим фич без валидированного спроса: палитра расширяется только из офферов.
